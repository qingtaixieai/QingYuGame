# 青屿 Opus 5.5 接手任务

## 工作树与接手顺序

- 本轮实际开发目录是 `online-scene-pixi/world-game` 工作树，分支 `codex/online-scene-pixi-20261110`，已提交基线 `1f7b497`。基线发布记录为 V32。交接时工作树含 56 个跟踪文件修改和 24 项未跟踪路径，包含 V33–V36 与撤离格回退。读取、保留这批本地增量，接手前用 `git status --short` 更新快照。当前生产状态需要实时验证。
- 先读 [代理接手](../代理接手.md)、[工程入口](README.md)、[交接索引](../交接索引.md)，再读 [模块归属](../../config/module-ownership.json)、[接口契约](../../contracts/http-routes.json)及 [最近工程审计](../superpowers/plans/2026-11-16-project-engineering-audit.md)。历史结论与当前代码有冲突时，记录差异并检查最近用户确认。
- 本轮确认的样式基线见 [撤离格记录](../superpowers/plans/2026-11-15-retreat-ring-appearance.md)。白灰填充都是 75% 透明，半径 34，描边宽 2、55% 不透明，保留浮现和下沉。

## 目标与边界

- Opus 先梳理现有实现、验证缺口和接手优先级。明确区分已实现、已测试、待实现与未核实。玩法规则、路由、数据、地图选择逻辑以现有行为为基准；新玩法另行确认。
- 模块化按职责拆分，优先检查共享场景画布的渲染和交互边界，同时评估高频状态传播及战斗动作编排。场景一至三级、探索与战斗复用现有模块；玩家与 NPC 路径经过相同的动作处理和游戏校验。
- 性能先基线、后优化。分别测镜头拖动与选格、陨石命中/受击数字、小船移动、实时广播/场景刷新。记录两次运行的条件、帧间隔 P95、长帧数与渲染调用或网络更新次数。隔离用例、联机实战和手机真机分别报告。
- 前端首版交付独立 HTML 预览，以青屿已有像素地图为视觉基准。地图全屏，侧栏收起，左下为选中目标，右上为脚下地点操作；底部热栏支持折叠。覆盖一级大陆、二级城镇、三级旅店和同图战斗的导航设计。原型使用示例数据；接入 React/Pixi 与现有后端契约安排在用户通过预览后的开发阶段。

## 接手步骤与验收

1. Opus 用深度推理提出模块、性能和验证意见。Opus 同时交付前端原型，主代理检查其产物的来源、运行和交互。API 交接读取约定文件及截图，项目文件的写入由主代理按项目确认流程执行。
2. 主代理整理负责人、目标文件、验收标准、已知风险与性能基线，交用户确认具体开发范围。开工后再按确认任务执行代码修改。
3. 每阶段使用独立代理验收，问题修复、复测并复验后再续下一阶段。契约变化运行 `python scripts/engineering_check.py`，后端回归使用隔离库，布局在 1280×800 和横屏 844×390 的浏览器验证。发布核对工作树、GitHub 和正式服的实际状态。

Git 推送、生产部署和线上数据写入分别按项目授权执行。

## Opus 审查与实施顺序

通过 Kiro 调用 `claude-opus-5-5`，请求 `thinking: adaptive` 和 `effort: high`。成功的审查响应包含思考流和完整正文。该审查读取了限定范围的源码和历史验收记录。测试和性能数字来自历史记录；Opus 本轮没有运行工作树。

| 阶段 | 负责人及范围 | 交付与验收 |
| --- | --- | --- |
| 1. 建立运行基线 | 主代理与验收岗。固定镜头、缩放、分辨率和场景，采集拖动、选格、浮沉、陨石命中及小船航行；后端复用现有广播采样方法。 | 留存可复跑场景与原始数据。分别记录 P95、超过 33ms 的帧数、每帧渲染次数；区分后台空闲、动画重叠和真实网络条件。 |
| 2. 收敛场景画布职责 | 前端地图岗维护 `SceneCanvas.tsx` 与场景坐标，战斗岗维护 `frontend/src/features/battle/vfx/`，主代理集成共享入口。优先核对独立动画循环和渲染触发重叠，测量证实后再改调度。 | 同一数据和输入下复测。桌面与横屏核对普通移动、目标格选择、撤离格浮沉、陨石命中和伤害数字。对比帧间隔与渲染次数，确认没有交互回归。 |
| 3. 验证实时状态与动作链 | 接口岗核对 `shared/worldSocket.ts`、`shared/protocol.ts` 与 `features/game/Game.tsx` 的缺省值、准备状态归属和连接生命周期。后端战斗岗追踪 `BattleService.java` 的玩家与 NPC 执行入口。 | 隔离库验证切场景、重连、连续战斗、回执重放、背包隐私。同一合法动作下，玩家与 NPC 通过相同游戏校验。只有可复现缺陷或明确测量收益才做对应代码改动。 |

Opus 建议抽查跨场景准备状态、旧连接事件和高 DPI 选格。主代理把它们列为验证项。模型建议的按执行方分支动作逻辑不采纳，玩家和 NPC 继续共用动作执行与结算；悬停属于客户端展示。现有选格模块、V36 回执、广播公共快照、连接生命周期保护均按已实现能力接手。

目前没有重复运行历史完整套件。上一份工程审计最终记录 171 项后端测试、22 项 JavaScript 检查、15 项 Python 测试，以及 6 连接本机广播 P95 77.8→38.0 毫秒。这是复跑参考，生产容量和手机真机性能仍需验证。
